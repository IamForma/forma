# CONFIG — конфигурация структуры проекта

Про устройство конкретно этого проекта — какие каталоги, какие файлы, за что каждый отвечает; растёт по мере целей, как `PROJECT.md`. Не путать с `manual/` в корне проекта — тот универсальный, не про этот проект и не меняется.

Девять разделов, по два на каждый «рабочий» узел (роль + документация, которую он формирует) и один центральный у `Core` — таблица ниже. Документация `Kit` (раздел 6) шире лога оснастки: несёт всю структуру проекта, файл/каталог за файлом, с сутью каждого.

---

## Девять разделов (по узлам)

Организующий принцип — по узлу: своя пара разделов на каждый из четырёх «рабочих» узлов (роль + документация, которую узел формирует), и один центральный раздел `Core`, вне пары. 4×2 + 1 = 9.

| № | Узел | Раздел | Суть | Где |
|---|---|---|---|---|
| 1 | `Intent` | Интервью | сбор брифа — что человек рассказал до первой цели, не переписывается по ходу | `project/brief/interview.md`, `history.md`, `reference.md` |
| 2 | `Intent` | Приёмка и сопровождение | сверка каждой задачи и круга по признаку, приём отчётов `Run`, ведение всего проекта в разговоре с человеком — `Intent` как единственная точка входа для человека | распределено намеренно, не по недосмотру: `GOAL.md` (история сверок), `ROADMAP.md` (что дала цель), `JOURNAL.md` (факты кругов) — три файла с разным родом записи, свести их в один означало бы дублировать то, что уже пишется на своём месте |
| 3 | `Spec` | Нарезка | деление круга на связанные карточки задач | `.devtool/features/` (карточка — верх), `spec.md` |
| 4 | `Spec` | Статистика и ценность | что нарезано и что в итоге получили как результат — стоимость/расход, из чего состоит продукт, для ясности понимания | `project/VALUE.md` — заводит `Spec`, зовёт `Intent` на закрытии цели (`intent-cycle-closing.md`, «After the verdict»; `spec-statistics.md`) |
| 5 | `Kit` | Работа и роль | снаряжение задачи: доступ, данные, умение, инструмент, модель | `kit.md` |
| 6 | `Kit` | Документация (оснастка) | вся структура проекта (что за файл/каталог, в чём суть) + лог: какой инструмент/доступ/скилл появился и какой разрыв закрыл | этот файл → раздел «6. Kit — Документация (оснастка)» ниже |
| 7 | `Run` | Работа и роль | исполнение ровно заданного выданными умениями, без импровизации | `run.md` |
| 8 | `Run` | Документация (по проекту) | итоговое описание сделанного, по карточкам рода «дело», для человека | `project/docs/` (по целям, `docs/goal-NN-<имя>/`) |
| 9 | `Core` | Центральный | вердикт круга целиком (не сумма пяти сверок), пороги, диагноз узла, тренд эффективности | `core.md`, `GOAL.md` → «Итог серии», `JOURNAL.md` |

**Пункты 2 и 4 закрыты.** Приёмка `Intent` остаётся распределённой — не пробел, а сознательный выбор не дублировать то, что уже пишется в `GOAL.md`/`ROADMAP.md`/`JOURNAL.md`. Статистика и ценность `Spec` получила свой файл — `project/VALUE.md`, заполняется на закрытии каждой цели.

## 6. Kit — Документация (оснастка)

Этот раздел (№6 в «Девять разделов» выше) несёт не только лог оснастки, а всю структуру проекта — `Kit` знает структуру именно затем, чтобы комплектовать: так же, как `Kit` комплектует `Run` под задачу (шесть единиц снаряжения — доступ, данные, умение, инструмент, модель, карточка), он комплектует любой узел, зная функционал каждого файла/каталога. Карта структуры и лог оснастки — одно знание, один раздел, не два разных.

### Технические контракты среды

Ограничения окружения, которые `Kit` обязан закладывать в снаряжение заранее, а не ждать, что `Run` заново продиагностирует ту же гочу. `PROJECT.md`, таблица «Оснастка узлов», держит только имя инструмента и одну строку-инвариант со ссылкой на конкретный якорь здесь — сам контракт (дата, причина, карточка-источник) живёт только тут, в одном месте.

Пишет `Kit` сразу, как факт найден — в отличие от «Лога оснастки» ниже, который пишется сводкой на закрытии цели (`kit.md`, «Разведка»/«Возврат»). Формат записи — заголовок с якорем (`#имя-контракта`), суть контракта, дата и карточка-источник.

#### Контракт `omitClaudeMd` {#omit-claude-md}

Факт (проверено чтением официальной документации Claude Code, `code.claude.com/docs/en/sub-agents`, раздел «Supported frontmatter fields»): субагент по умолчанию получает весь `CLAUDE.md` (пользовательский + проектный + локальный), если это явно не отключено полем фронтматтера `omitClaudeMd: true`. Правило: задача класса «текст-в/текст-аут, без маршрутных решений» снаряжается субагентом `extractor` (`extractor.md` в каталоге ролей Claude, `omitClaudeMd: true`), не `general-purpose` — тот молча тащит в контекст весь протокол, который такой задаче не нужен.

Записей о находках конкретно этого проекта пока нет — следующие появятся, как только среда впервые преподнесёт сюрприз.

### Лог оснастки

Справочник по оснастке самой системы: какой инструмент, доступ или скилл появился и какой разрыв закрыл. Не хронология — хронология в истории каждой карточки; здесь только вывод, годный на будущее.

**Пишет `Kit`, хозяйством, на закрытии каждой цели** (`kit.md`, «Конфиг»; вызывает `Intent`, `intent-cycle-closing.md`, «After the verdict»). Источник — свои (ресурс/инструмент/скилл) карточки эпика «3. Форма/Intent+Kit», закрытые с прошлой сводки.

**Читает `Kit` при снаряжении**, раньше внешних источников готового (скилл `skill-authoring`, «Источники готового»): разрыв мог уже закрываться в прошлой цели.

#### Шаблон записи

```
### <инструмент/доступ/скилл> — цель N, круг M

**Закрыл разрыв:** <что не работало или чего не было>
**Карточка-источник:** `.devtool/features/done/<файл>.md`
```
