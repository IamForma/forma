# Конфигурация проекта

Заполняется под конкретное дело и живёт весь проект. Правила — `AGENTS.md`, они не меняются.

Здесь — чем и на каком уровне работаем. Что строим и в каком порядке — в `ROADMAP.md`. Сегмент — в `goals/goal-NN/GOAL.md`.

**Язык проекта** *(человек, до старта; определяет язык карточек задач, целей и документации — `AGENTS.md` §6)*: Документация самой схемы (`manual/`) под язык проекта не переводится: она существует только на английском — оригинал, `manual/en/` — и русском — точная копия, `manual/ru/`.

**Что делаем** *(человек, до старта)*:

**Шаблон проекта** *(человек, при установке; по этому полю `Intent` выбирает ветку пятой позиции интервью — читает, а не выводит по наличию файлов)*:

| Поле | Значение |
|---|---|
| Имя | — |
| Источник | — |
| Статус | `нет` |
| Маршрут | `project/ROUTE.md` — референс для пятой позиции интервью |

**Три возможных статуса, закрытый список:** `готовый проверенный` — маршрут пройден до результата, пятая позиция сводится к сверке; `формируется с человеком` — маршрут записан частично, сверка по записанному и построение по недостающему; `нет` — зона неизвестная, маршрута не существует, все пять позиций прорабатываются в одинаковом объёме. Сценарий интервью при этом один и тот же и приходит с ядром: шаблон добавляет только референс в пятую позицию.

**Эпики проекта** *(человек, до старта; роль и процедура каждого — неизменны, `intent.md`, «Эпик», код в скобках сверяет их между собой; имя в этом столбце — единственное, что здесь настраивается под проект)*:

| Код | Эпик в этом проекте | Функционал |
|---|---|---|
| `value` | 1. Ценность/Intent+Kit | замечание по расходу производства самого проекта — токены, кэш, заходы, цена круга: `Core` читает тренд, `Intent` держит «дёшево» |
| `docs` | 2. Документация/Intent | документация по самому продукту, для человека: пользовательская, для администраторов, техническая — как работать с тем, что производим. круг цели закрыт, и данное ею обещание надо показать сдержанным: `Intent` читает зоны «Результат» закрытых карточек, смотрит на живой результат и пишет раздел `project/docs/` для человека |
| `forma` | 3. Форма/Intent+Kit | узел дошёл до строки «человек» в маршруте; там же разведка `Kit` по незнакомому стеку до нарезки |
| `result-image` | 4. Образ результата/Intent | интервью `grilling` на открытии новой цели |
| `core` | 5. Замечания Core/Core+Intent | предложения `Core` при закрытии круга: `Core` пишет замечание, `Intent` разводит по доменам |
| `incoming` | 6. Входящие/Intent | корректировка или задача, появившаяся по ходу работы, которую не нужно сразу отправлять в производство: `Intent` либо быстро решает её сам и закрывает карточку, либо отправляет в нарезку `Spec`. Сюда же — карточка без нарезки и дефект вне текущей цели |
| `goal` | 7. Производство/SKRIC | сам продукт: главная цель `goal-goal` и подцели `goal-NN` в одной дорожке, цель выбирается меткой |
| `experience` | 8. Опыт/Intent+Kit | прополка хранилища `project/experience/`: разъехавшиеся ключи, противоречащие записи |
| `review-image` | 9. Ревью образа/Intent | вне производственного цикла. Собственный процесс тестирования человека, который он сформировал сам для себя: как проверяется результат, коррективы по работе и тестированию, дополнения к тому, что нужно было получить в конечном результате — образ результата и конечная приёмка/тестирование могут отличаться. Это дополнение к уже сформированной цели, не её переписывание: `GOAL.md` не меняется (запрет 8), дополнение записывается рядом, и только человек превращает его в новую цель или переоткрытие. Своя процедура тестирования, связанная с отдельными процессами |

**Эпик — вид цели, цель — метка.** Девять видов идут параллельно; у каждого главная цель `goal-<код>` и, если нужно, подцели `goal-NN` (сквозная нумерация). Карточка несёт ровно одну метку цели в `labels` — это истинная связь; эпик только дорожка вида (`AGENTS.md` §6, `intent-goal-opening.md`, «Эпик»). Кто формирует цель каждого вида — там же, «Как формируются цели».

**Виды документации** *(человек, решение по проекту; какие виды вообще существуют здесь — это список, а не обязанность: какие из них должна конкретная цель, говорит её образ результата, эпик «4. Образ результата/Intent»)*:

| Вид | Для кого | Что в нём |
|---|---|---|
| | | |

**Список видов — не обязанность каждой цели.** Проект объявляет, какие виды здесь бывают; какие из них должна конкретная цель, называет её образ результата. Цель, чей образ о документации молчит, не должна ни одного — дописать вид задним числом значит расширить обещание после того, как оно дано, а это переоткрытие образа человеком, не решение узла.

**Где лежит.** `project/docs/goal-NN-<имя>/`, по файлу на вид. Раздел цели накапливается кругами, а не пересобирается: каждый закрытый круг дописывает своё.

**Пороги** *(человек, до старта; `Core` пересматривает только через остановку с докладом)*:

| Порог                        | Значение                                                                           |
| --------------------------------- | ------------------------------------------------------------------------------------------ |
| Заходов на задачу  |  |
| Объём круга, карточек (на эпик) |  |

Расход в токенах и срок — статистика, не пороги: пишутся по факту (AGENTS.md §3), не задаются и не спрашиваются. В долларах предел не задаётся.

**Квалификация узлов** — не отдельное поле, не заполняется заранее. У каждого узла свой источник уровня, читается на месте, когда узел реально смотрит на задачу:

| Узел | Источник уровня |
|---|---|
| `Intent` | бриф/интервью — узнаёт по ходу разговора, кто в этой области судит результат |
| `Spec` | `ROADMAP.md`/`GOAL.md` конкретной цели — как здесь принято резать работу, на месте, при нарезке |
| `Kit` | свой поиск арсенала (скилл `skill-authoring`, «Источники готового») — сам сверяет, чем работать |
| `Run` | карточка + снаряжение, выданное `Kit` — уровень уже в задаче, отдельно называть не нужно |
| `Core` | не варьируется по проекту — фиксированная роль протокола (`PROTOCOL.md`, «Квалификация») |

Уровень течёт по цепочке документов, которые и так перед узлом (бриф → `ROADMAP.md`/`GOAL.md` → карточка → снаряжение), а не хранится отдельной строкой, которую человек обязан выдумать до старта.

**Справочники проекта** *(человек; то, чему результат обязан соответствовать во всех кругах)*:

---

**Чего не хватало — не здесь.** Настройка этого поля неизменна (правило зафиксировано, запрет 5 `AGENTS.md`): само поле заполняет `Intent` на каждый круг в `JOURNAL.md` (хвост, не эта таблица); находка, требующая починки, а не только фиксации, — карточка `.devtool/features/`, эпик «3. Форма/Intent+Kit», метка `чего-не-хватало`. `PROJECT.md` держит только это правило, не сами находки — иначе неизменяемый файл настроек станет растущим журналом.

## Что попадает в кэш круга

Из этого файла в кэш идут: оснастка узлов, пороги, доступы и данные, справочники проекта — ссылкой и версией. Образ результата приходит отдельно — из `GOAL.md` текущей цели.

Не идёт: «Чего не хватало» (`JOURNAL.md` + карточки эпика «3. Форма/Intent+Kit») — это материал для `Spec` на нарезке, а не фон для каждого вызова.
