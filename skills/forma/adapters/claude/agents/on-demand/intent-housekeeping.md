# Schema/tooling housekeeping — `Kit` executes, `Intent` confirms

Read this file when a card touches **the project's own schema/tooling** (schema files, service directories, keeping the engine files in step with `AGENTS.md`, lifting `guard-delete.sh`) — epic "3. Form/Intent+Kit", schema/reference-file kind. Shared rules — `.claude/agents/kit.md`, "Infrastructure" (execution) and `.claude/agents/intent.md`, "Housekeeping" (confirmation).

**`Kit` carries out schema-file edits and service-directory tidying, as internal tooling** (`.claude/agents/kit.md`, "Infrastructure" — you write yourself the six units, do it, put the result in "Result," the way `Run` normally does). This covers editing schema files (`AGENTS.md` — the law itself — `.claude/rules/claude-8.md`, `.agents/rules/gemini-8.md`, `.codex/CODEX-8.md`, `.claude/agents/*.md`, `.agents/plugins/forma/agents/*.md`, `.codex/roles/*.md`, `.claude/skills/*/SKILL.md`, `PROJECT.md` tables), and tidying service directories — moving, renaming, deleting the outdated, restructuring (`.devtool/`, `.forma/manual/`, `project/`, `VARS/`, etc.). Boundary mark unchanged: a project file changes, not the site's state, and the decision doesn't move the open goal's end-image closer — otherwise it's work, and it goes the normal route as a separate card. Writing any of these texts — the rules in skill `skill-authoring` (writing text an agent reads).

**`Intent` never makes this edit itself.** Once `Kit` reports the change: read what actually changed, verify parity where it applies, check nothing broke or contradicts across the schema, then report to the human — the same outward-voice duty as every other confirmed card, not a live-in-conversation watch replacing a check. Find something `Kit` missed — return the card to `Kit` (`todo`+`"Kit"`), don't fix it inline yourself.

**The protocol's law lives in `AGENTS.md`, once — `.claude/rules/claude-8.md`, `.agents/rules/gemini-8.md` and `.codex/CODEX-8.md` carry no copy of it.** Sections 1–7 exist in exactly one file, the same for every engine; each engine file is a thin wrapper carrying only its own section 8, "Engine architecture" — where the role files sit, which models the nodes run on, how a subagent is invoked, which fields of a call carry the spend of §3, where hooks and MCP are configured. How that section reaches a session is the engine's own business: `.agents/rules/gemini-8.md` and `.codex/CODEX-8.md` open with the import line `@AGENTS.md`, while `.claude/rules/claude-8.md` carries none — there §1–7 are read natively from `AGENTS.md` and §8 is printed into the session by a SessionStart hook. **Editing a rule means editing `AGENTS.md` and nothing else**; there is nothing to carry over in the same pass, because there is no second text. Putting any part of §1–7 back into an engine file — even a short quote "for convenience" — recreates the very thing this construction removed: two sources of truth for one schema, drifting apart silently. Equally, an engine-specific path, model name or field name in `AGENTS.md` is a defect: it belongs to that engine's §8.

**What still has two copies is the roles** (`.claude/agents/*.md` ↔ `.agents/plugins/forma/agents/*.md`, including the "on-demand" layer): no standard unifies a role's declaration across engines, so the old discipline holds there unchanged — same breadth of explanation, same structure, differing only in engine-specific frontmatter; a divergence in meaning OR in scope between them is a defect; shrinking only in sync, never one side alone. Verify both at once with `node .claude/scripts/sync-engines.cjs --check`: it reports the root-rules construction on its own line (is `AGENTS.md` there, do both wrappers import it, has anything engine-bound leaked into it) and the eleven role pairs as a table. Roles are no longer copied between engines — neither by hand nor by script: each engine keeps its own adapter, verified by its own conformance test, and role parity is shown by `--check` as information only. Any commit in the project, a plain `git commit` included, runs the pre-commit hook (`forma-commit.cjs --sync-staged`), which checks the core and the adapters and stops the commit on a breach; it writes nothing into `.agents/` or `.codex/`.

**No manual edits to the engine.** Every change to the engine — the dashboard, board scripts, hooks, helper scripts, templates, schema files, roles (the files that ship from the protocol source, `.forma/protocol/`) — is made so that it reaches the protocol source: either made in the source and synced into the project, or made in the project and carried into the source in the same pass. A change left only in the project copy is a manual edit: the next sync or reinstall overwrites it and the defect returns. Such a change is never "finished" until the source holds it; the card's `## Result` names where in the source it landed.

**Carrying to the protocol, and pushing.** A schema edit in the project is carried into the protocol source in the same pass, not as a later step; before committing there, grep the carried files for the project's own names (site, domain, stack) — the template never takes this project's content. Committing is fine at once; **`git push` only on the human's explicit command.** Only the project root is yours: neighbouring directories next to it belong to others — not read, not edited, not proposed for deletion.

**Deleting system directories and schema files via Bash/PowerShell is blocked by the `.claude/hooks/guard-delete.sh` hook by default.** Protected paths: `.claude/`, `.agents/`, `.codex/`, `.devtool/`, `.forma/manual/`, `.forma/living/`, `VARS/`, `AGENTS.md`, `.claude/rules/claude-8.md`, `PROJECT.md`, any `GOAL.md` (the engine wrappers `.agents/rules/gemini-8.md` and `.codex/CODEX-8.md` are covered by their directories). It's lifted for a single action by the human's exact phrase "Отключи сенсорику": you create the marker `.claude/hooks/.delete-unlock`, the hook lets the next destructive call through and erases the marker itself — the next deletion is blocked again and needs the same phrase anew.

**The same phrase, said about a task or instruction rather than about deletion, needs no marker file.** It authorizes the node currently addressed to act outside the established route or rules for that one task, once — and prohibition 11 requires the fact to be written down in the same breath, not after. Where: a card is already open for the task — a line in that card's `## History`, the same format as any other event (`` `Node`, YYYY-MM-DD: <what was bypassed and why, one or two sentences> ``); no card is open — a `.devtool/features/` card, epic "3. Form/Intent+Kit" (the same epic that already keeps every other fact a node can't leave unrecorded elsewhere, `AGENTS.md` §2). Either way, prohibition 11 is why it's written down — this file only names where.

**Confirming a tooling card, check two habits** (`kit.md`, "Infrastructure"): the tool is named by function, not provider; a mass replacement left `.devtool/features/`, `.forma/living/CHANGELOG.md` and `.cache/` untouched. Either broken — a discrepancy, back to `Kit`.

**"Executes itself" means authored the content, not dispatched the call that produced it.** Dispatching a schema-free subagent (`extractor.md`, `omitClaudeMd: true`) for a bounded text transform on a schema file — e.g. compressing prose without cutting facts — is not self-execution, provided you didn't write the content yourself and do a real line-by-line comparison against the original afterward, not a trust in the subagent's own report. The distinction is who authored the words, not who issued the dispatch: routing a call and confirming its output stay two different acts even when the same node does both, as long as the confirmation is substantive. This is narrower than the `Kit`-executes rule above — only a bounded transform, with no judgment about what the schema *should* say, dispatched by you to a subagent carrying none of the schema itself.

**A short mechanical task is the one named exception to prohibition 1 (`AGENTS.md` §5) — you execute it yourself.** A change of literally named values (what was → what becomes) across an explicitly listed set of files, no interpretation required, within epics "3. Form" or "8. Experience": `Intent` may execute it directly, without `Kit` and without a separate confirming node. A card is still opened (the five fields) and its history names this exception explicitly — never silent, never the default route. Outside this case, doer and confirmer remain separate nodes. (A costlier alternative — `Core` batch-reviewing accumulated short tasks — is documented in `core.md`, not active; turning it on is a `PROJECT.md` decision.)

## Claude Code adapter: zones, reconciliation, wiring

**Zone of edits.** Claude Code edits its own files (`.claude/`) and the shared `AGENTS.md`. `.codex/` is Codex's, `.agents/` and `GEMINI.md` are Gemini's: a divergence found there is named to the human as a fact, not fixed by hand, and another engine's result is checked only on the human's direct command. Nothing is carried over between engines: `sync-engines.cjs` only checks, and each engine keeps its own adapter; nothing in another engine's zone is ever edited by hand. Why: an engine editing another's configuration brings in assumptions about an environment it never verified.

**Engine reconciliation.** The commit check (`forma-commit.cjs --sync-staged`) checks the core and this adapter only; Codex and Gemini findings neither print nor stop there. The full cross-engine check — `node .claude/scripts/sync-engines.cjs --check` — is run by hand before every release. It verifies the core's integrity and this adapter's conformance test (`claude-economy.test.cjs`); role parity with other engines is shown there as information, not as a breach.

**Core ↔ adapter (`.forma/dashboard/lib/engines.cjs`).** The core names no `.claude/` path; it finds `.claude/forma-adapter.cjs` — instruction weight, tool journal, usage parser, transcripts dir, role/§8/skill paths, dashboard view (`.claude/scripts/dashboard-view.cjs`: settings, MCP names, transcripts). A field missing — `unknown`, never 0. Form checked by `.claude/scripts/forma-adapter.test.cjs`. The interview skills live in the core (`.forma/skills/`) and are delivered into `.claude/skills/` at installation.
