# forma — установка протокола «Форма»

Копирует протокол в текущий проект двумя слоями. **Ядро** (`core/`) — одно для всех движков и ставится всегда: закон `AGENTS.md` §1–7, `manual/`, каркас `project/`, дашборд с модулем экономики (`dashboard/economy.cjs`, `tally.cjs`, `spend-line.cjs`), доска (`board/`, заготовка `.devtool/features/`), оба интервью (`skills/`), `living/`. **Адаптер движка** (`adapters/<движок>/`) — §8, роли, хуки, скрипты, скиллы и свой адаптер экономики; ставится выбранный. Готов один — `adapters/claude/` (Claude Code, по умолчанию); `adapters/codex/` и `adapters/gemini/` перенесены как есть и помечены `NOT-READY.md` — **не ставятся**, пока у них нет теста соответствия. В составе: общие правила, пять ролей-агентов, хук защиты от удаления, универсальную документацию схемы (`manual/`) и пустой каркас структуры проекта (`project/`, общий для обеих сред). Ничего не придумывает и не подстраивает под проект — переносит как есть; заполнение под конкретное дело (пороги, доступы, эпики, цели) происходит позже, при открытии первой цели, самим `Intent` в разговоре с человеком (`agents/intent.md`, «Хозяйство»).

## Установка — один вызов установщика

Файлы не копируй руками — это делает установщик `bin/forma.cjs` этого же плагина (тот же, что `npx github:IamForma/forma init` из терминала). Порядок:

1. **Задай человеку три вопроса в чате, по одному** (на повторной установке — те же, ответы по умолчанию годятся):
   - **движки** — Claude Code (готов); Codex, Gemini — «скоро», не ставятся. По умолчанию `claude`;
   - **шаблон проекта** — `none` (свой маршрут вырабатывается в интервью, по умолчанию) или имя из `templates/` (шаг 8 ниже — развилка, реши вместе с человеком);
   - **канбан-доска** — `auto` (найти CLI `code`/`antigravity-ide`/`antigravity`, поставить Kanban Markdown, где его нет) или `skip`.
2. **Запусти в корне проекта:** `node <skill-dir>/../../bin/forma.cjs init --engines <движки> --template <шаблон|none> --board <auto|skip>`. Все три флага заданы — установщик вопросов не задаёт.
3. **Покажи человеку итог установщика как есть:** что синхронизировано, тронут ли `project/`, строки Kanban Markdown (`✓ ок` / `✓ установлено` / команда для ручной установки), строку сверки `sync-engines --check`. Итог не `✓` — разбери и доложи (шаг 8b).

Повторный запуск — обновление: конфигурация схемы перезаписывается, `project/`, доска `.devtool/features/`, `living/` и файлы записанного шаблона не трогаются. Шаги ниже — справка о том, что установщик делает; вручную по ним идёшь только для неготовых адаптеров по прямой просьбе человека (3b, 3c).

## Что делает установщик (справочно)

0. **Сначала создай или сохрани Git-границу целевого проекта.** Выполняй этот шаг в корне целевого проекта, до копирования любого файла из шаблона. Запусти `node <skill-dir>/../../scripts/initialize-project-git.cjs .`. Это Node-сценарий без зависимости от PowerShell или `sh`; Node уже нужен протоколу для скриптов и дашборда и доступен во всех поддерживаемых движках.

   Скрипт сначала проверяет, что `git` доступен в `PATH`. Если Git недоступен, **сразу остановись и сообщи человеку**, что для установки нужен Git; не копируй ни одного файла протокола и не создавай `project/`. Если в корне нет `.git`, скрипт выполняет `git init` именно в этом корне и создаёт базовый `.gitignore`, только когда такого файла ещё нет. Если `.git` уже есть (в том числе файл рабочей копии), скрипт не трогает ни историю, ни remote. В обоих случаях скрипт держит секреты окружения по запрету 15: дописывает строку `.env` в `.gitignore`, если её там нет (остальное не меняет); создаёт `.env` в корне из `core/.env.example`, только если `.env` ещё нет — существующий с ключами не перезаписывается; кладёт `.env.example` рядом, если его нет. `.env` не коммитится никогда, `.env.example` — коммитится.

1. **Две категории целей, два разных правила — не одно общее «спроси, если есть».**
   - **Конфигурация схемы** — всё из шагов 2–6 и служебные скрипты (`.claude/rules/claude-8.md`, `.claude/agents/`, `.agents/rules/gemini-8.md`, `.agents/plugins/forma/`, `.codex/`, `.claude/hooks/*`, `.claude/scripts/*`, `manual/`; `living/` — не конфигурация, см. шаг 6). Она одинакова для любого проекта и не редактируется вручную (`AGENTS.md` §2, «Housekeeping» — эти файлы обновляет `Intent` напрямую, не производственным маршрутом). Поэтому: **синхронизируй всегда, без вопросов** — пути нет, создай; путь уже есть, перезапиши содержимым шаблона как есть, молча. Расхождение с шаблоном — либо более старая версия (обновить и надо), либо ручная правка вопреки правилу (тоже надо перезаписать: два источника правды у одной схемы не заводим).
   - **Установленный шаблон проекта сильнее ядра на своих файлах.** Если в `project/PROJECT.md`, блок «Шаблон проекта», записано имя шаблона (не `нет`), всё, что этот шаблон кладёт в проект (его `skills/<имя>/` в плагине `templates/<шаблон>/`, `project/SITE.md`, `project/ROUTE.md`, `project/brief/idea.md`, `.claude/scripts/` — `site.cjs`, `site-php.cjs`, `loco-pipeline.py`, `po_shift_check.py`, `tokenator_translator.py`), ядро **не перезаписывает никогда** — даже при совпадении имени со скиллом ядра. Такой путь пропускается молча и называется в отчёте шага 9: «оставлено версией шаблона `<имя>`». Обновить эти файлы может только установщик самого шаблона, по просьбе человека.
   - **`project/` целиком** (шаг 7) — специфика конкретного проекта: пороги, цели, бриф, величины, всё, что человек и `Intent` наполнили содержимым по ходу дела. **Не трогай вообще, если каталог `project/` уже существует в любом виде** — ни одного файла или подкаталога внутри не создавай, не перезаписывай, даже не сверяй по отдельности. Каркас (семь файлов + восемь каталогов) создаётся только при самой первой установке, когда `project/` в корне проекта нет совсем.
   - В конце (шаг 9) отчитайся: что синхронизировано в конфигурации, тронут ли `project/` (да — только на первой установке, иначе никогда).

2. **Скопируй общие правила — три файла, не один.** Закон протокола (§1–7) живёт одним файлом, одинаковым для любой среды; у каждого движка остаётся только своя §8 «Архитектура движка» (где лежат роли, на каких моделях, как вызывается субагент, из каких полей читается расход):
   - `core/AGENTS.md` → `AGENTS.md` в корне проекта — **источник правды, правится только он**;
   - `adapters/claude/rules/claude-8.md` → `.claude/rules/claude-8.md` — §8 Claude Code, без строки импорта. **Корневой `CLAUDE.md` не создаётся**: Claude Code v2.1.277+ сам читает `AGENTS.md` и `.claude/rules/`; специфика движка пишется только в его §8-файле. Найден `CLAUDE.md` в корне при обновлении — перенеси его уникальное содержимое в `.claude/rules/claude-8.md` и спроси человека об удалении (фраза «Отключи сенсорику»); `sync-engines --check` называет его нарушением;
   - `adapters/gemini/rules/gemini-8.md` → `.agents/rules/gemini-8.md` в корне проекта (шаг 3b) — та же строка плюс §8 Antigravity.

   Копии §1–7 в двух файлах-обёртках быть не должно ни при каких обстоятельствах — это два источника правды у одной схемы. Проверяется машинно: `node .claude/scripts/sync-engines.cjs --check` разбирает конструкцию отдельной строкой «Корневые правила» и падает, если обёртка потеряла импорт, если `AGENTS.md` нет, или если в `AGENTS.md` просочился путь либо поле, принадлежащие одному движку.

   Все три среды читают `AGENTS.md` нативно: Claude Code (v2.1.277+) и Codex — как корневой файл, Antigravity — ещё и через импорт в `gemini-8.md`. Среда без нативного чтения (Amazon Bedrock, отключённая телеметрия) — фолбэк шага 4a.

3. **Скопируй пять ролей.** `adapters/claude/agents/*.md` → `.claude/agents/` в проекте (создай каталог, если его нет). Файлы обобщены — доменных подробностей конкретного дела в них нет; если найдёшь такие при чтении — это баг, доложи человеку, не исправляй сама.

   **Плейсхолдеров в `tools:` не бывает.** Список `tools:` во фронтматтере роли копируется как есть и должен быть рабочим сразу: имени вида `mcp__<что-то>__*` с угловыми скобками — баг шаблона, а не задание установщику: в свежем проекте такое имя не разошьётся ни в какой инструмент. Нашла такое — доложи человеку, не подставляй значение сама. MCP-инструменты, специфичные проекту (сайтовый адаптер, свой API и т.п.), в ядро шаблона не входят вовсе — их вписывает `Kit` при снаряжении (`agents/on-demand/kit-project-kitting.md`) или привозит компаньон-пресет под конкретную среду (например, `forma-wordpress-novamira` — Novamira MCP).

3b. **Скопируй Gemini-сторону (Antigravity).** Тот же протокол, для среды Google Antigravity/Gemini, — параллельно шагам 2–3, не вместо них:
   **Адаптер не готов** (`adapters/gemini/NOT-READY.md`): по умолчанию шаг пропускается и называется в отчёте шага 9; выполняется только по прямой просьбе человека, как есть. Все пути отсчитываются от каталога с этим `SKILL.md`.
   - `adapters/gemini/rules/gemini-8.md` → `.agents/rules/gemini-8.md` в корне проекта — обёртка Antigravity: импорт `@AGENTS.md` плюс §8 своей среды (шаг 2 выше). Своей копии §1–7 не несёт.
   - `adapters/gemini/plugin.json` → `.agents/plugins/forma/plugin.json`.
   - `adapters/gemini/agents/` → `.agents/plugins/forma/agents/`, **рекурсивно, вместе с `on-demand/`**. Не используй маску `agents/*.md`: PowerShell не захватывает вложенный каталог. Перед копированием создай именно каталог назначения, затем выполни: `New-Item -ItemType Directory -Force .agents/plugins/forma/agents | Out-Null; Copy-Item -Recurse -Force <skill-dir>/adapters/gemini/agents/* .agents/plugins/forma/agents/`. После этого должны существовать шесть файлов в `.agents/plugins/forma/agents/on-demand/`.
   - `adapters/gemini/mcp_config.json` не переносит настройки MCP: в комплекте он намеренно содержит пустой объект `mcpServers`. Не перезаписывай существующую конфигурацию проекта; конкретные серверы добавляет `Kit` или человек после решения об оснастке.

3c. **Скопируй Codex-сторону.** **Адаптер не готов** (`adapters/codex/NOT-READY.md`): по умолчанию шаг пропускается и называется в отчёте шага 9; выполняется только по прямой просьбе человека, как есть. Шаблон — `adapters/codex/` в каталоге этого же скилла (пути отсчитываются оттуда):

   - `adapters/codex/.codex/CODEX-8.md` → `.codex/CODEX-8.md` и `adapters/codex/.codex/CLAUDE-COMPAT.md` → `.codex/CLAUDE-COMPAT.md` — **§8 этой среды** и исполнимая граница с каноническими ролями Claude. Своей копии §1–7 не несут, корневой `AGENTS.md` остаётся источником.
   - `adapters/codex/.codex/config.toml` → `.codex/config.toml` — **кроме секций `[mcp_servers.*]`**: MCP всегда специфичен проекту, покажи человеку и оставь заполнение `Kit`/человеку, тем же порядком, что `mcp_config.json` (3b) и `.mcp.json` (Claude-сторона).
   - `adapters/codex/.codex/agents/*.toml` → `.codex/agents/` — пять определений субагентов и механический `extractor`.
   - `adapters/codex/.codex/roles/*.md` → `.codex/roles/` — адаптеры пяти ролей и `extractor`. **Оба вида обязательны:** TOML говорит, чем агент запускается, Markdown направляет к полному каноническому телу Claude; не копируй роль вторым смысловым текстом.
   - `adapters/codex/.codex/roles/on-demand/*.md` → `.codex/roles/on-demand/` — слой «по требованию». **Не пропускай его:** закон ссылается на эти файлы по голому имени (§2, §5 и далее), и без них узел Codex не найдёт инструкцию, на которую его послали. Это короткие адаптеры, ведущие к каноническим Claude-процедурам; `sync-engines.cjs` проверяет их ссылку и структуру, а не побайтное совпадение текста.
   - `adapters/codex/.codex/hooks.json` → `.codex/hooks.json`; `adapters/codex/.codex/hooks/*.ps1` → `.codex/hooks/` — проверки старта, защита удаления и журналирование на PowerShell. **Это не «недоделанный Bash»:** правка shell-хуков переносится сюда по смыслу, не копированием.
   - `adapters/codex/.codex/tests/*.ps1` → `.codex/tests/`.
   - Проектные навыки Codex обнаруживаются из `.agents/skills/`. После того как установлены `.codex/` и канонические `.claude/skills/`, выполни `node .codex/scripts/sync-codex.cjs --apply`, затем `node .codex/scripts/sync-codex.cjs --check`. Скрипт зеркалит **каждый** каталог `.claude/skills/<name>/` вместе со всеми вложенными файлами и обновляет манифест. Не копируй этот набор выборочно вручную: `verify-parity.ps1` проверяет динамический состав и все файлы. MCP-секции не входят в шаблон и добавляются только после решения человека.

   **Два отличия этой среды, которые не надо «чинить».** Потолок параллельных потоков — три (вместе с главной сессией это все четыре слота среды); поднимать не следует. Расход по §3 здесь не измеряется — конфигурация не отдаёт агенту полей токенов и кэш-чтения, и закон отвечает прямо: **не оценивать и не писать нули**, а записывать, что поля были недоступны.

4. **Скопируй хуки.** `adapters/claude/hooks/guard-delete.sh` → `.claude/hooks/guard-delete.sh`; `adapters/claude/hooks/check-ready.sh` → `.claude/hooks/check-ready.sh`; `adapters/claude/hooks/check-plugin-update.sh` → `.claude/hooks/check-plugin-update.sh`; `adapters/claude/hooks/check-dashboard.sh` → `.claude/hooks/check-dashboard.sh`; `adapters/claude/hooks/tool-usage.sh` → `.claude/hooks/tool-usage.sh`; `adapters/claude/hooks/intent-start.sh` → `.claude/hooks/intent-start.sh`; `adapters/claude/hooks/check-card.sh` → `.claude/hooks/check-card.sh`; `adapters/claude/hooks/check-clean-zone.sh` → `.claude/hooks/check-clean-zone.sh`. На Unix-подобной системе выставь исполняемый бит (`chmod +x`) всем восьми. `intent-start.sh` — тоже `SessionStart` (`startup`): подаёт основной сессии роль `Intent` и `intent-session-start.md`, показывает человеку ссылку на дашборд (`AGENTS.md` §1). `check-card.sh` и `check-clean-zone.sh` — `PostToolUse` с матчером `Write|Edit`, двумя записями в одном матчере: первый проверяет карточку доски в момент записи, второй сообщает о следе проекта в чистой зоне (запрет 16). `guard-delete.sh` и `tool-usage.sh` подключаются через `PreToolUse`; `check-ready.sh`, `check-plugin-update.sh` и `check-dashboard.sh` — через `SessionStart` (матчер `startup`, для `check-plugin-update.sh` `timeout` 15) — в `.claude/settings.json` проекта, все три отдельными записями в одном матчере, порядок между ними не важен. `check-dashboard.sh` держит дашборд самовосстанавливающимся (перезапускает `dashboard/serve.js`, если тот не отвечает); `tool-usage.sh` пишет лог обращений к инструментам для вкладки «Борт». `check-plugin-update.sh` говорит, когда на GitHub появилась версия плагина новее установленной, и молчит в любом другом случае — включая отсутствие `gh` или сети. **Команды «обнови» у протокола нет намеренно:** о команде надо помнить, а хук срабатывает сам; обновление запрашивается словами в живом разговоре, и скилл `forma` отзывается на них по своему описанию. Если файла настроек ещё нет, создай его с этими записями, если есть, добавь их, не заменяя остальное.

4a. **Фолбэк подачи §8.** `adapters/claude/hooks/load-engine-section.sh` → `.claude/hooks/load-engine-section.sh`, **не регистрировать**. Нативное чтение `.claude/rules/` проверено фактом на v2.1.278, но не документировано: если пропадёт, запись хука в `.claude/settings.json` (`SessionStart`, матчер `startup|resume|clear`) возвращает §8 одной правкой. Пока чтение работает, регистрация даст §8 дважды.

4b. **Скопируй служебные скрипты.** `adapters/claude/scripts/*` → `.claude/scripts/` в проекте: `sync-engines.cjs` для 100% паритета двух движков, `external-model-bridge.cjs` для моста к внешней модели, `build-done-cards-graph.cjs` для сборки графа опыта по закрытым карточкам, `session-economy.cjs` для замера перечитывания против работы по стенограммам движка, `tool-usage.cjs` для разбора лога хука `tool-usage.sh`.

4c. **Интервью и доска — ядро; адаптер их доставляет.** Сначала ядро: `core/skills/` → `skills/` в корне проекта (оба интервью — источник), `core/board/` → `board/` (`new-card.cjs`, `check-board.cjs`, `DATA-MODEL.md`), `core/.devtool/features/` → `.devtool/features/` (заготовка доски; при обновлении карточки не трогаются — только довези папку, если её нет). - не выдумывает содержание `PROJECT.md`/`ROADMAP.md`/целей — каркас пуст, заполнение это работа `Intent` в разговоре с человеком, не установки;
