# Стиль кода движка

Для кода ядра (`skills/forma/core/`), адаптера Claude, установщика (`bin/`, `scripts/`) и тестов. Проверяется `npm run lint` там, где правило машинное.

## Имена

- Файл — по задаче: `check-board.cjs`, не `utils2.cjs`. Инструмент — по функции, не по поставщику.
- Функция — глагол + объект: `readCards`, `checkRouteStage`. Булево — `is`/`has`: `hasId`.
- Константа модуля — `UPPER_SNAKE`: `ROUTE_SINCE`, `STAGE_KEYS`.
- Сокращения — только общепринятые (`dir`, `re`, `fm`); однобуквенные — в лямбдах на одну строку.

## Функции

- Одна функция — одно дело. Длина — до ~40 строк; больше 60 — предупреждение линтера (`max-lines-per-function`).
- Параметров — не больше 4 (`max-params`); больше — объект.
- Модуль, который и библиотека, и CLI, экспортирует функции и запускает `main()` только под `require.main === module`.

## Ошибки

- Ошибка не глотается: пустой `catch {}` запрещён (`no-empty`). Ожидаемое отсутствие данных — `catch` с комментарием, что именно ожидается и что возвращается.
- Нет данных — `unknown`/`null`, не `0`: ноль и «не записано» различаются.
- Неверный ввод CLI — сообщение и ненулевой код выхода, не молчаливое значение по умолчанию.

## Общие помощники

- Обход каталога, разбор аргументов, frontmatter карточки, путь доски, даты правил — одна копия в `lib/`, не заново в каждом файле.
- Ядро не зависит от адаптера движка: зависимость — только в сторону ядра.
- Данные движка ядро берёт только через `dashboard/lib/engines.cjs` (адаптер — `forma-adapter.cjs` в каталоге корня с точкой); форма и замена отсутствующего поля — в шапке модуля; в коде ядра нет имён движков и путей их каталогов.

## Проверки

Проверка — модуль реестра, не ветка в длинной функции: `{ id, since, run(ctx) }` (форма и запуск — `dashboard/lib/checks.cjs`). Скрипт только гоняет реестр по кругу; порядок строк в реестре — порядок находок в выводе.

- `id` — латиница через дефис, равен имени файла. `since` — ключ правила в `living/checks.json` или `null`: день вступления пишет проект, проверка получает его как `ctx.since`. `run(ctx)` возвращает массив строк-находок; пустой — чисто. Сведения, что не нарушения, — готовой строкой в `ctx.info`.
- Два реестра, по принадлежности: проверки доски — ядро, `board/checks/index.cjs`; проверки сверки движка — `.claude/scripts/checks/index.cjs` (свои — рядом, ядровые — подключены по пути). Проверка ядра в каталоге адаптера не живёт.
- **Новая проверка — один новый файл и одна строка в реестре**, плюс случай порчи в `test/helpers/check-cases.cjs` (что портим, какая находка обязана появиться) и, если правило датировано, ключ в `living/checks.json`. `npm test` сам проверяет, что файл есть в реестре, а `id` равен его имени.
- Помощник, нужный нескольким проверкам, — в `support/` рядом с реестром: не в файле проверки и не в соседней проверке.
- Текст находки изменился осознанно — `UPDATE_GOLDEN=1 npm test` и просмотр разницы; рефакторинг вывод не меняет.

## Тесты

- `npm test` — `node:test`, без зависимостей. Поведение фиксируется на проекте-фикстуре (`test/fixture/`): чистая установка + синтетические карточки, без следов реальных проектов.
- Рефакторинг — без изменения поведения: `npm run baseline:save` до, `npm test` (или `npm run baseline:diff`) после.
- Новая проверка отличает успех от провала: тест с порчей фикстуры падает, без порчи — нет.

## Линтер

- ESLint — только зависимость разработки протокола (`devDependencies`), в проекты не ставится.
- Вендорный код (`skill-creator`) и адаптеры других движков не линтуются.
