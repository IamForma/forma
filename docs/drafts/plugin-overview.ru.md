# Черновик: описание плагина «Форма» для README

> Черновик. Составлен по установке плагина через `npx` в пустую папку, разбору установленных файлов
> и прогону хуков на тестовых данных. Перед переносом в README — сверить с текущей версией.

## Что это

«Форма» превращает одного агента Claude Code в команду из пяти ролей с общим законом и доской задач.
Установщик (`npx github:IamForma/forma init`) кладёт в проект протокол, роли, хуки, доску, дашборд и мануал;
повторный запуск — безопасное обновление: `project/`, доска и `.forma/living/` не затираются.

## Как работает

**Пять узлов.** Каждый узел — отдельная роль со своей зоной ответственности:

| Узел | Роль |
|---|---|
| **Intent** | главная сессия: говорит с человеком, держит цели, открывает и закрывает круг |
| **Spec** | превращает намерение в задачу с проверяемым критерием готовности |
| **Kit** | подбирает инструменты и исполнителя, собирает задание |
| **Run** | исполнители по предмету работы (текст, изображение, сайт, механическая работа, визуальная проверка) |
| **Core** | проверяет результат против критерия и выносит приговор |

**Карточка задачи.** Работа идёт карточками в `.devtool/features/` (Kanban Markdown). У карточки — задача,
комплект, история попыток, результат, критерий готовности и бюджет попыток. Хук проверяет формат карточки
в момент записи, поэтому сломанная карточка видна сразу.

**Маршрут.** Задача проходит узлы по маршруту; на доработку возвращается одним путём, а не «как получится».
Это главная защита от типичной проблемы агентов — «сделал что-то и объявил готовым».

**Один закон на три движка.** Общие правила (§1–7) лежат в `AGENTS.md` и одинаковы для Claude Code,
Codex и Gemini (Antigravity). Специфика движка — отдельным файлом (§8): `.claude/rules/claude-8.md`
и аналоги. Расхождения между движками ловит проверка `sync-engines --check`.

**Хуки Claude Code** (`.claude/settings.json`):
- `guard-delete` / `unlock-delete` — запрет удаления без явного разрешения человека;
- `check-card` — проверка карточки при каждой записи в доску;
- `intent-start` — при старте сессии вводит главную сессию в роль Intent и даёт ссылку на дашборд;
- `check-ready`, `check-dashboard`, `check-plugin-update` — готовность проекта, дашборд, новая версия;
- `tool-usage` — журнал использования инструментов для учёта расхода.

**Дашборд** — локальная веб-страница: доска, цепочка узлов, расход токенов, закон, мануал; два языка (en/ru).

**Проверка установки.** `node .forma/verify/verify-install.cjs` сверяет установленное с описью
(`.forma/install-manifest.json`) и называет каждое расхождение: адрес, ожидаемое, найденное.

## Сильные стороны

- Дисциплина вместо доверия: критерий готовности, бюджет попыток, единый канал возврата.
- Один источник правил для трёх движков, проверка расхождений автоматическая.
- Установщик сам проверяет установку; повторный запуск — обновление, а не перезапись.
- Покрытие тестами: около 240 поведенческих тестов, включая «тесты порчи» — каждая проверка
  доказанно ловит свою поломку и не ловит чужие.
- Хуки быстрые (порядка 15 мс на вызов) — на скорость работы не влияют.

## Слабые места и что улучшить

1. **Уведомление о новой версии не срабатывает.** `check-plugin-update.sh` отбрасывает версии
   с суффиксом (`0.4.186-alpha`) и смотрит только в кэш маркетплейса и только при наличии `gh` CLI —
   у установивших через `npx` уведомления нет вовсе. Решение: брать установленную версию
   из `.forma/install-manifest.json`, принимать суффиксы, обходиться без `gh`.
2. **Версия не видна при установке.** Она пишется в `.forma/install-manifest.json`, но не печатается.
   Решение: выводить её в первой строке установщика (`Forma 0.4.186-alpha → <папка>`).
3. **Защита от удаления обходится** через `git clean`, `find -delete`, `fs.rmSync`, `mv` наружу.
   Полной защиты на уровне шаблонов не будет, но частые обходы стоит закрыть.
4. **Тяжёлый стартовый контекст.** В каждую сессию входит ~56 КБ инструкций (`AGENTS.md` ~30 КБ,
   §8 ~4 КБ, Intent ~22 КБ) — порядка 14–18 тыс. токенов до первого слова пользователя, и снова
   после каждого сжатия контекста. Кандидаты на вынос «по требованию»: шаблон карточки и таблица
   видов работ из §6, детали роли Intent.
5. **Плагин меняет настройку пользователя.** `settings.json` проекта задаёт
   `CLAUDE_CODE_AUTO_COMPACT_WINDOW=200000` — это перекрывает личную настройку; стоит убрать
   или явно описать в README.
6. **Хуки требуют bash.** На Windows нужен Git Bash; без него хуки молча не работают.
   Установщик должен прямо об этом говорить.
7. **Опора на чтение `AGENTS.md` движком.** Протокол рассчитывает, что Claude Code читает `AGENTS.md`
   при отсутствии `CLAUDE.md`. Это стоит проверить вживую и описать запасной путь
   (`load-engine-section.sh`) в README.
8. **Нет сквозного теста с живым агентом.** Тесты проверяют установщик и скрипты, но не то,
   что агент следует протоколу. Даже один сценарий «создай карточку → она проходит `check-board`»
   поймает регрессии в инструкциях.
9. **Порог входа.** Установка → интервью → перевод заготовки. Для знакомства полезна
   демо-карточка, проходящая весь маршрут Intent → Core за несколько минут.

## Как узнать установленную версию

- В проекте: поле `version` в `.forma/install-manifest.json`.
- Последняя выпущенная: страница Releases репозитория или `.claude-plugin/plugin.json` в `main`.
